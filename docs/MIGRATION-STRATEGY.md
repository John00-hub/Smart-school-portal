# Multi-Tenant Migration Strategy

**Migration:** `supabase/migrations/0002_multitenant_grading_publishing.sql`
**Scope:** audit findings H2 (tenancy), H3 (grade scales), H5 (publishing)
**Status:** written and syntax-validated. **Not executed against a real database.**

Per instruction, this strategy is documented *before* the migration is run
anywhere real. Read this first.

---

## Why multi-tenancy is required

Commercialising through Midex Edits means one deployment serving many
independent Nigerian private schools. Without tenant isolation, School A's
administrator would see School B's students, results and announcements. That
is not a cosmetic problem — it is a data-protection failure and would end a
pilot immediately.

The instruction was explicit that isolation must be enforced **in the
database, not the interface**. This design does that.

---

## The three changes and why they are in one migration

They are coupled. Splitting them would create an intermediate state where
grades are computed inconsistently:

1. **Grade scales become per-school** (H3). Requires a settings table.
2. **`results.grade` can no longer be a generated column** — a stored
   generated column cannot read a settings table, and would not recompute
   when a school edits its bands. This is forced by change 1.
3. **`school_id` on every tenant table** (H2) — and the grade trigger needs
   the student's school to pick the right scale, so it depends on 2.

---

## What the migration does

| Step | Action | Reversible? |
|---|---|---|
| A1 | Create `grade_scales`, `grade_bands`; seed default scale | Yes (drop tables) |
| A2 | **Drop and re-add `results.grade`** as a plain column | ⚠️ Destructive — see below |
| A3 | Add `set_result_grade()` trigger; backfill existing grades | Yes |
| B1 | Add `is_published`, `published_at`, `published_by` to `results` | Yes |
| B2 | Add publish-authorisation trigger + `teacher_publish_results()` RPC | Yes |
| B3 | **Rewrite the `results: read scoped` policy** to require `is_published` for parents/students | Yes |
| C1 | Create `schools`, `school_members` | Yes |
| C2 | Add nullable `school_id` to 16 tables + indexes | Yes |
| C3 | Create a demo tenant; **backfill all existing rows into it** | ⚠️ Semi-destructive |
| C4 | Add `assign_school()` trigger so new rows inherit the caller's school | Yes |
| C5 | Add **RESTRICTIVE** tenant-isolation policies to 14 tables | Yes |
| C6 | `platform_create_school()` RPC | Yes |

### The one genuinely destructive step

**A2 drops `results.grade`.** The values are immediately regenerated by the
trigger and backfilled from `ca_score + exam_score`, so no information is
lost *provided* `ca_score` and `exam_score` are intact. They are the actual
source data; `grade` was always derived.

Still: **take a backup before running this.** Supabase → Database → Backups,
or `pg_dump`. The rollback section below assumes you have one.

## Key design decisions

### Why RESTRICTIVE policies for tenant isolation

Postgres combines **permissive** policies with `OR`. Adding another permissive
policy would *widen* access, not narrow it — the opposite of what isolation
needs.

**RESTRICTIVE** policies combine with `AND`. So a row is visible only if:

```
(a role policy from 0001 permits it)  AND  (it belongs to the caller's school)
```

This is the correct mechanism and it means the existing 41 role policies keep
working unchanged. It is also the single most important line in the migration
to get right — a permissive policy here would silently expose every school to
every other.

### Why `current_school_id()` is `SECURITY DEFINER`

The caller's school must be resolved from `school_members`, not asserted by
the client. Making the function `SECURITY DEFINER` lets RLS policies call it
even though the policy itself runs with the caller's privileges. The client
never supplies a `school_id` anywhere in this design.

### Why `is_platform_admin()` exists

Midex Edits staff need to operate across schools. A platform admin is defined
as an `admin`-role profile with **no** `school_members` row — they belong to
no single school, so they see all. A school's own admin *does* have a
membership row and is therefore confined to their school. This distinction is
deliberate and should be tested before going live.

### Why existing rows go to a demo tenant

Leaving `school_id` NULL would orphan all existing data once the restrictive
policies activate — every row would become invisible to everyone. Backfilling
into a demo tenant keeps the current data working and gives the first pilot
school a starting point.

## Risks and how they are mitigated

| Risk | Severity | Mitigation |
|---|---|---|
| `grade` values lost in A2 | High | Backup first; trigger + backfill regenerate from CA/exam scores |
| Restrictive policy accidentally permissive | Critical | Verified by reading the emitted SQL; `check_policies.cjs` asserts drop/create pairing. **Must be re-verified by testing cross-school access.** |
| Orphaned rows after C5 | High | C3 backfills every table before policies activate |
| `assign_school()` raises for users with no membership | Medium | Correct behaviour, but will break any existing session until memberships exist — C3 creates them |
| Publishing gate hides already-shared results | Medium | All existing rows default to **unpublished**. Communicate to pilot schools that results must be explicitly published after the migration |
| Grade bands changed after results exist | Low | New results use current bands; historical grades are **not** rewritten. This is correct for academic records but must be explained to schools |

## Pre-flight checklist

Run these **before** the migration, on a copy if possible:

```sql
-- 1. Confirm row counts you expect to preserve
select 'results' t, count(*) from public.results union all
select 'students', count(*) from public.students union all
select 'profiles', count(*) from public.profiles;

-- 2. Confirm every result has the scores needed to regenerate its grade
select count(*) from public.results where ca_score is null or exam_score is null;
-- must be 0

-- 3. Record current grades so you can diff afterwards
create table if not exists public._pre_migration_grades as
  select id, grade from public.results;
```

## Post-flight checklist

```sql
-- 4. No result left without a grade
select count(*) from public.results where grade is null;      -- must be 0

-- 5. Grades unchanged (they should be identical)
select count(*) from public.results r
  join public._pre_migration_grades p on p.id = r.id
 where p.grade is distinct from r.grade;                       -- expect 0

-- 6. Every row has a tenant
select count(*) from public.students where school_id is null;  -- must be 0

-- 7. Every tenant table has a restrictive isolation policy
select tablename, policyname, cmd from pg_policies
 where policyname = 'tenant isolation' order by tablename;     -- expect 14 rows
```

If step 5 returns a non-zero count, the grade bands in `grade_bands` do not
match what the old `grade_for_total()` produced. Compare before trusting.

## Rollback

There is no automatic down-migration. Rollback means restoring the backup
taken before step A2.

If you must roll back manually, the minimum is:

```sql
-- remove tenant isolation
do $$ declare t text; begin
  foreach t in array array['students','teachers','parents','classes','subjects',
    'teacher_assignments','enrollments','results','attendance','timetables',
    'announcements','academic_sessions','terms','parent_student_links']
  loop execute format('drop policy if exists "tenant isolation" on public.%I', t);
  end loop; end $$;

-- restore the generated grade column
alter table public.results drop column if exists grade;
alter table public.results add column grade text
  generated always as (public.grade_for_total(ca_score + exam_score)) stored;
```

This does **not** restore the original `results: read scoped` policy — you
would need to re-run that block from `0001/schema.sql`.

## What is deliberately NOT done yet

- **No frontend tenant awareness.** The app still assumes a single school.
  Reads will work because `current_school_id()` scopes them, but there is no
  UI to switch schools or manage branding.
- **No per-school subject or session configuration UI.**
- **No `school_id` on the `activity_logs` read policy** — it inherits
  isolation, but the admin-only policy was not re-tested under it.
- **The migration has not been executed anywhere.** Syntax is validated by
  the PostgreSQL 18 parser; semantics have not been exercised.

These are the next phase, not this one.
